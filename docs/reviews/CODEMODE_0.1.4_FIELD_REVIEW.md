# 0.1.4 现场复核：一次 40 万 token 压缩保留了什么

- 日期：2026-10-28
- 版本：pi-vcc-codemode 0.1.4（本会话的压缩摘要由 0.1.4 生成）。
- 会话：单个 codemode 会话，单次手动压缩（`reason: manual`）；压缩前 **402,653 tokens**。
- 证据：摘要 6,504 字符、46 个引用、6 处省略标记。本文只记录聚合数与机制判断，不保存、不引用会话正文；原始会话与统计脚本在本地 git-ignored 目录。
- 关联：[0.1.4 审阅与修订计划](../plans/CODEMODE_0.1.4_REVIEWED_PLAN.md)、[0.1.4 实施记录](../patches/0.1.4-brief-and-metadata.md)。

## 1. 结论

**这是一份合格的“导航索引”，但还不是 400K 任务在固定预算下的“续接均衡点”。**

- 若问“接任者能否知道下一步做什么、去哪读细节”：**能**。任务合同、阶段图、停止条件、交付规则都在，46 个引用全部可解析。
- 若问“接任者能否不 recall 就判断完成度、验证结果和发布状态”：**不能**。两份决定性报告各只剩 64 字；`[Session Goal]` 里的 HEAD/版本/提交状态仍是任务开始时的快照。

更准确地说：**规模到了，分配没到。** 6.5K 字符对 402K tokens 是约 0.4-0.5%，作为索引是合理的；但预算的形状偏向“过程广度”，而不是“末端结论深度”。

## 2. 阅读体验

- **第一眼可信。** 开头能看到目标、仓库、权威计划、被否决项、停止条件和交付规则；一个没有上下文的接任者知道先读哪份计划、哪些事不能做。
- **中段疲劳。** `[assistant]` 里有 24 条同构的 `* codemode goal: … (#N)`，每条约 59 字，合计 1,413 字；扫读时很难快速判断哪些调用是关键，哪些只是探针。
- **末尾失配。** 读到“全部阶段完成、未提交”时，会以为这是当前状态；但摘要生成之后已经完成提交、打 tag 和推送，真正的状态在压缩后的 live 消息里。不 recall 就无法确认“900 tests / 0 fail”、真实会话 A/B 的数字或发布是否完成。

## 3. 方法与口径

读取本次压缩记录（compaction entry）及其摘要，按下列口径统计；不打印正文：

- 摘要长度 = `summary.length`；`[Session Goal]`、`[Files And Changes]`、`[user]`、`[assistant]`、note 按字符区间切分。
- 引用 = 摘要中 `#N` 去重后，按会话的 `#N` 空间解析到消息条目；统计角色、是否存在无法解析的引用。
- 省略率 = 所有 `[omitted X of Y chars; recall #N]` 的 X、Y 求和；长文本候选的最小摘录为 64 字。
- 原文对照 = 被引用/被省略消息的源文本长度、角色与可见片段长度；只用长度和布尔值，不输出内容。
- 预算口径 = 0.1.4 的 `budget = round(clamp(15 × historyBlockCount, 1100, 2000) × charsPerToken)`；本次记录 `briefHistoryMessageCount = 274`（15×274 已被 2,000 上限截断）。`details` 未记录实际 `charsPerToken`，下文按 3.1-3.8 字符/token 估算，不断言精确超/欠。

## 5. 保留了什么

- **任务合同与护栏**：目标、仓库、权威计划路径、被否决的 B/H2/+44、开工前 3 步、**停止条件 3 条完整保留**、交付规则（不提交/不含 `research/` 等）。这些是防漂移的部分，保留得最好。
- **阶段图**：R1、R3、R4、R5/R6、R7、最终校验、Pi 1.0 兼容检查，以及“全部阶段完成、未提交”。
- **真实会话阶段**：21 个 codemode 会话、重放器、异常/误报/工作树清理，均以 goal 行加引用保留。
- **失败证据**：8 条错误调用带 `{error observed; result #N}`，失败链可追。
- **0.1.4 目标缺陷在真实 400K 压缩中确实修好了**：没有 `intent:`，`sections` 无正文标签，没有孤立 `(#N)` 行，note 395 未变。H9（limited note）在本会话没有可观察样本。

需要区分“不可见”与“丢失”：上述内容大多能通过 `recall`/`scan` 取回，**代价是多一次调用，以及不知道该 recall 哪一条的风险**。真正会误导的是状态快照，它是“错的陈述”，不是“省略”。另外，本次压缩发生在发布请求之前，提交/推送由压缩后的 live 消息承载；所以“未提交”是压缩时点的真实状态，不是摘要 bug。下一次压缩合并 live 消息后，旧状态行会不会继续留在 `[Session Goal]`，才是需要观察的点。
## 7. 机制：为什么预算会偏向“过程”

1. **64 字下限 + “便宜的整段升级”先花光助手配额。** 助手文本候选先各取 64 字；短消息按“升级到全文的增量最小”优先补全；最后才按“最新优先、每次 +64”分配剩余额度。本次助手配额约 1,500 字，18 条保留文本各 64 字，加上若干短行的全文升级后已不足 64 字，于是 3,973 字的最终报告和 2,560 字的 A/B 汇总都停在下限。**过程旁白比结论更占预算。**
2. **工具预算被 codemode 行占满。** 24 条 goal 行花掉 1,413 字；错误结果有 20% 的保留通道，8 条错误各带 result 引用；剩余条目（包括直接 `bash`/`test` 调用）被折叠成一条“109 earlier tool-call entries omitted”。**未标记错误的调用没有 result 引用，直接工具没有可见行。**
3. **用户配额 40% ≈ 2,000 字 < 首条消息 2,452 字。** 首条消息的中段因此被切掉 596 字；`[Session Goal]` 又重复了同一条消息的开头约 475 字（占摘要 7.3%），进一步挤压，但不是截断的唯一原因。
4. **文件清单只认 write/edit/apply_patch 类调用。** 本会话的源码改动多由 `research/patch-*.ts` 脚本在 bash 中完成，fileOps 看不到，于是“Modified”列的是临时补丁脚本，真正的 `src/`、`tests/` 只出现在“Read”。
5. **`[Session Goal]` 是跨压缩合并的。** 它按行去重、上限 8 行；旧的状态行不会自动刷新，可能一直留到被新行挤出。note 里“Session Goal is a condensed excerpt”的提醒在文末，而 goal 在文首，警示来得太晚。

## 8. 均衡点判断

| 标准 | 判断 |
|---|---|
| 规模（固定预算） | **合理**：6.5K 字符 ≈ 2K tokens，占 402K 的 0.4-0.5%；46 个引用、0 错位；预算基本用满。 |
| 作为索引 | **合格**：知道读哪份计划、哪些事不能做、每个细节大概在哪。 |
| 作为续接快照 | **不合格**：末端证据（验证、A/B、发布状态）最薄；无 error 标记的调用结果与直接工具没有导航；状态行过期。 |
| 作为 400K 任务的均衡点 | **尚未达到**：一句话——“负担得起的索引，但还不是可信的终点状态”。 |

如果接任者愿意先 recall 两份报告，它足以继续工作；如果它直接相信摘要里的“完成/未提交”，就会得出错误结论。均衡点的标准不应是“摘要能独立回答一切”，而应是“摘要能让人知道**现在最该核实什么**”；这一点本次没有做到。

## 9. 建议（同预算，按性价比排序）

1. **末端加权。** 给“最新的长助手报告”留一个固定配额（例如 400-600 字），在“短行全文升级”之前分配；或把 64 字步进放到全文升级之前，先保证最新报告有足够头部。24 条 goal 各 59 字、两份报告各 64 字，是当前最不划算的分配。
2. **无 error 标记的调用也给 `result #N`。** 至少给最后 N 条无 error 标记的调用配对结果引用；错误优先通道保留。这样“补丁是否应用、测试是否跑过”可以从摘要直接跳转，而不是靠猜索引。
3. **保留直接工具证据行。** codemode 会话里给 `bash`/测试命令/exit code 留一个小配额；本次 109 条 tool-call 全被折叠、直接工具 0 行，是最终验证不可见的直接原因。
4. **去重与状态降级。** `[Session Goal]` 与首条用户消息开头去重；把 HEAD/版本/提交状态标为“as of 首条消息”，或从 goal 提取中排除这类快照；把 note 的“not current state”提醒放到 goal 附近。
5. **fileOps 兜底。** 记录脚本内编辑，或在压缩时用 `git diff` 补一份真实改动文件；至少不要让临时研究脚本挤掉 `src/`、`tests/`。
6. **审计指标。** 除“超预算/引用可解析”外，建议加：最终报告保留字符数、无 error 标记调用的结果引用数、直接工具行数、goal 重复字符数、状态行年龄（距首条消息的条目数）。这些指标只输出聚合，不输出正文。

## 10. 与 0.1.4 范围的关系

- 0.1.4 的可观察目标（`goal:` 标签、真实章节名、limited note 剥离、动作标签、引用位置）在本次真实压缩里**没有回归**：24/24 goal、`sections` 无正文标签、note 395、0 个无法解析引用。
- 本文讨论的是**分配形状**，不属于 0.1.4 的修复清单；改动它会触及冻结的预算公式/借额顺序/夹具，需要新计划、新测试（T14 预算矩阵、golden 冻结规则）和审阅，不应顺手改。
- 0.1.4 审计的“0 超预算”是必要条件，不是充分条件：它证明预算没有溢出，不证明预算花在了最有价值的内容上。真实会话的“最终报告只剩 64 字”属于后者。

## 11. 局限

- 只有一个会话、一次手动压缩；没有第二次压缩来验证合并后的状态行行为。
- 预算利用率按 3.1-3.8 字符/token 估算（`details` 未记录 `charsPerToken`，debug 关闭），未断言精确超/欠。
- 本次压缩发生在发布请求之前；提交/推送/发布是压缩后的 live 消息，所以“未提交”在当前上下文里已被覆盖。摘要本身没有错，错的是把它当作当前状态。
- 这不是任务结果实验；“影响”是按接任者行为做的分析判断。真实会话的原始数据与重放脚本留在本地 git-ignored 目录，本文只保留聚合数。
