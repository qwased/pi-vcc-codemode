## 0. 结论摘要

1. **札记的 A/C/D/E/F 验证可信；H 的方向正确，但“丢弃率 27%”和“引用覆盖 100%”是整分支/渲染阶段口径，不能直接外推到 350K。** 60K 会话实际被摘要的窗口只有 26 条 codemode 调用，`CODEMODE_SEGMENT_CHARS=1000` 保留 25 条，丢掉的那 1 条按算法正是最早的一条。
2. **预算：5K 可以作为大窗口的上限候选，10K 宜做可选项，不宜直接做默认。** 只加 token 预算会被 `maxBlocks=80` 和选块策略吃掉；要同时提高块上限，并先做“意图账本 + codemode goal 加分”。
3. **第 N 次压缩提示：长程可见性确实缺失，但“前 N-1 次简报在哪里”今天没有真实答案。** 旧 compaction 摘要不在 `#N` 索引里，也没有 recall 入口；应加“覆盖声明”，而不是指向不存在的旧简报。真正需要的是 P2 的 goal/constraint 状态或跨压缩去重的意图账本。
4. **中文：简报本身不是空白；结构化提取大面积空白。** 后续改目标、用户偏好、blocker（Outstanding Context）对中文基本不生效；长中文段落还可能整段进不了 Session Goal。补规则前要先决定是否改变“无 codemode 记录与上游一致”的契约。

## 1. 方法与口径

本次讨论使用了三类证据：

1. **代码核对**：预算、选块、渲染、合并、recall 索引和中文提取的具体实现位置。
2. **本机真实压缩窗口的聚合统计**：只统计条数，不读正文。分别观察“窗口内 codemode 调用 → ranked 选块后 → 段渲染后 → 存储摘要”的逐层保留。
3. **合成压力测试**：用于说明机制在更大窗口下的趋势，不作为统计结论。

需要区分两个容易混淆的分母：

- **整条分支的未排名简报**：审计脚本的 `segments` / `quota` 使用这一口径。它包含已经被保留尾部覆盖的消息，也包含所有历史段。
- **实际存储摘要的输入窗口**：以最后一次 compaction 的 `firstKeptEntryId` 为边界，只包含被摘要的消息。札记中的 52 条是前者，存储摘要的 28 行是后者的一部分。

札记的 `references.coverage=100%` 只覆盖“进入简报后又被 8 行/字符额度丢掉”的行，**不覆盖 ranked 选块阶段丢掉的行**。60K 时 ranked 恰好保住了摘要窗口内的全部 codemode 调用，所以 100% 成立；窗口变大后，这个数字不能沿用。

三个测量样本：

| 样本 | tokensBefore | 压缩次数 | context edit | 口径 |
|---|---:|---:|---|---|
| 60K 会话 | 61,728 | 1 | 无 | 精确重建摘要窗口 |
| 72K 会话 | 72,002 | 1 | 无 | 精确重建摘要窗口 |
| 167K 会话 | 167,622 | 5 | 有 | 按原始分支重建，未应用 Pi 的 session projection；绝对数字为近似值 |

## 2. 对现场札记的复核

### 2.1 已确认成立的部分

- A（guideline 前缀）、C（可操作省略标记）、D（去掉 `×N`）、E（补抽 nested 文件操作）、F（touched / 下钻覆盖 nested）都在代码和真实压缩里有对应证据。
- “真正的约束已经从行数变成字符”在 60K–72K 的形状下成立：每段保留最后 8 行后，字符额度决定还能补回多少条。
- `recall range` 把省略从“只知道少了东西”变成“知道去哪取”，这是 0.1.2 最有价值的接口改动之一。

### 2.2 需要修正的口径

60K 会话的实际摘要窗口测量：

| 阶段 | 数量 |
|---|---:|
| 被摘要消息数 | 54 |
| 归一化块数 | 54 |
| 窗口内 codemode 调用 | 26 |
| ranked 选块后块数 | 28 |
| ranked 选块后 codemode 调用 | 26 |
| 段渲染 quota 0 后的 codemode 行 | 8 |
| 段渲染 quota 1000 后的 codemode 行 | 25 |
| 存储摘要中的 codemode 行 | 25 |

结论：

- ranked 选块保住了窗口内全部 26 条调用。
- 段渲染 quota 0 只保留 8 条；quota 1000 恢复到 25 条，仍然丢 1 条。
- 按“从保留尾部向前补回连续 codemode 行”的算法，被丢的 1 条正是**最早**的那条。所以“只丢 1 条”和“最早意图被省略”并不矛盾：丢的是长程任务最需要的开头。

72K 会话的实际摘要窗口测量：

| 阶段 | 数量 |
|---|---:|
| 被摘要消息数 | 36 |
| 归一化块数 | 35 |
| 窗口内 codemode 调用 | 17 |
| ranked 选块后 codemode 调用 | 17 |
| 段渲染 quota 0 后的 codemode 行 | 8 |
| 段渲染 quota 1000 后的 codemode 行 | 17 |
| 存储摘要中的 codemode 行 | 8 |

这个会话的存储摘要只保留 8 条，呈现 quota 0 的形态；按 0.1.2 的 quota 1000，17 条可以全部保留。它是 H 对中小窗口有效的直接例子。

### 2.3 札记中值得保留的建议

- 简报末尾明示保留尾部的编号区间：成本极低，能消除“最后的结论被吃掉”的误判。
- 非 codemode 丢弃行明示“不可恢复 / 没有 recall range”：避免 agent 空跑一次 `vcc_recall`。
- 用 `--quota 0,400,800,1000,1200` 的曲线记录 H 的代价：比只报一个丢弃率更能说明取舍。

## 3. 问题一：是否有必要进一步放宽预算

### 3.1 当前的三层限制

| 层 | 当前限制 | 代码位置 |
|---|---|---|
| ranked 选块 | floor 1100 / ceiling 2000 tokens；最多 80 块；最近 16 块优先；同分按新近度 | `src/hooks/before-compact.ts:761`、`src/core/rank.ts:42` |
| 段渲染 | 每段保留最后 8 条工具行，再向前补回连续 codemode 行，最多 1000 字符 | `src/core/brief.ts:383`、`src/core/brief.ts:273` |
| 跨压缩合并 | 总 120 行，新简报优先；Session Goal 只留 8 行 | `src/core/summarize.ts:197`、`src/core/format.ts:31`、`src/core/summarize.ts:84` |

### 3.2 大窗口的真实数据

对本机 167K tokens 会话的最后一次压缩窗口（181 次 codemode 调用，原始分支重建，近似值）分别调整 ceiling 和 `maxBlocks`，只统计本次窗口的新简报部分：

| ceiling tokens / maxBlocks | 简报中的 codemode 行 | 占比 | 省略标记 |
|---|---:|---:|---|
| 2000 / 80（当前） | 11 | 6% | 无 |
| 5000 / 80 | 47 | 26% | 无 |
| 10000 / 80 | 47 | 26% | 无 |
| 5000 / 200 | 82 | 45% | 有 |
| 10000 / 200 | 106 | 59% | 有 |
| 10000 / 400 | 122 | 67% | 有 |

三件事：

1. **5K/10K 确实有显著价值。** 当前配置只保留 6%，5K/10K 配 200 块可以到 45%–59%。
2. **只加 token 预算不够。** 10K/80 和 5K/80 一样，因为 80 块上限先触顶。必须同时提高 `maxBlocks`。
3. **当前配置下的丢失是静默的。** 2000/80 和 5000/80 都没有省略标记：170 条左右的意图在 ranked 选块阶段消失，既没有行，也没有“这里省略了”的提示。这正是“最早几次意图被省略”的机制。

合成压力测试也能复现趋势：200 轮 × 12 次调用（2400 条意图）时，当前 80/2000 只保留 5 条；10K/400 保留 100 条。该数字只说明机制，不是统计结论。

### 3.3 成本

- 简报不是一次性成本，而是每轮重发，直到下一次压缩。
- 仓库基准记录：大 session 的约 8K 字符简报绝对覆盖率只有约 17%–20%（`benchmarks/README.md:163`）。
- CHANGELOG 记录过一次“提高 ceiling 和 block 预算没有带来差别”的实验（`CHANGELOG.md:211`）。这说明更大的简报不是自动更好，选块质量比容量更关键。
- token 估算的 chars/token 被限制在 2–6；中文/代码混合会话的真实比例可能更低，10K token 预算不一定等于 10K 实际 token，最终要用真实 usage 校准。

### 3.4 建议

1. **先做意图账本。** 从被摘要窗口收集所有合法的 `// goal:`，按文本去重，保留首次出现，输出成独立的 `[Codemode Intents]` 段，并带 `#N`。100 条意图约 8K 字符、按 6 字符/token 约 1.3K token，比 10K 原始行更密。
2. **给 codemode 调用加分。** 当前带 goal 的 codemode 调用只是普通 `tool-call` 12 分，低于 edit 34、test 26、user 18（`src/core/rank.ts:117`）。有声明意图的调用应得到更高权重，否则会被用户消息和助手正文挤出 80 块池。
3. **H 的额度先试 1500–2000。** 60K–72K 窗口在这个范围就能保住全部意图；大窗口再试 3000–4000。
4. **5K 作为大窗口上限候选；10K 做可选项。** 如果采用 5K，必须同时把 `maxBlocks` 提到 200–240；10K 默认会显著增加每轮成本和跨压缩合并压力。
5. **审计脚本增加 ceiling / maxBlocks 扫描。** 至少报告：每个会话形状的意图保留率、总摘要 token、旧简报保留、以及行为结果（压缩后的正确下一步/重复工作）。没有这些，不应把 10K 设为默认。

一言以蔽之：**5K 可以接受；10K 默认太粗。先修“选谁”和“保最早意图”，再谈“装多少”。**

## 4. 问题二：是否要加“第 N 次压缩 / 旧简报在哪里”的提示

### 4.1 计划已经给出的答案

- §1.2 非目标：不做“所有用户消息永久 pin”“无限状态进入固定预算”或“字节级旧简报回注”。
- §2：简报只能是当前状态和导航的有界视图，不能承担完整历史存储。
- §4.2 / P2：`pi-vcc.current-task` 单键状态（goal/constraints/next/sourceRefs），按分支重放、整体替换，目标是在 1/5/10 次压缩后仍可见。P2 目前暂停。
- P5 才做 1/5/10/20 次压缩的确定性重放；§11 记录旧简报保留中位约 40%，H 的行为测量尚未完成。

因此，计划对“长程任务多次压缩”的答案是：**当前状态 + recall 导航**，不是携带旧简报本身。

### 4.2 当前实现的实际行为

- 只合并 Pi 传入的最近一次 `previousSummary`。头部区各有 cap（Session Goal 8 行、Files 每类 10 条、Commits 8 条等），transcript 合并是 120 行总预算且新简报优先（`src/core/summarize.ts:197`、`src/core/summarize.ts:84`）。
- 压缩次数多了，早期 goal 和旧简报行会被静默丢掉；留下的只有 `...(N earlier lines omitted)` 这种没有 `range` 的标记。
- recall 只索引 `type:"message"` 条目（`src/core/global-indices.ts:17`、`src/core/load-messages.ts:26`）。compaction 摘要不在 `#N` 里，也没有别的读取入口。
- 因此“旧简报在 session 文件的 compaction entries 里”对持有文件的人成立，对 agent 不成立：它既不在上下文，也不可检索。

### 4.3 建议

1. **加“覆盖声明”，不加“旧简报指针”。** 例如：
   `Compaction #N; this summary covers the current window; earlier summaries are not in context; original entries remain recallable via vcc_recall.`
   同时在新摘要的 `details` 里记录 `compactionIndex` 和经过校验的 ref/数量；旧摘要没有这些字段就省略，fail-closed。
2. **不要声称连续的 `#A–#B` 范围。** 只有 provenance 可追踪时才输出 range；计划 §4.4 也是这个要求。分支会话的全局索引可能包含非当前分支条目。
3. **修掉 merge 阶段的死路标记。** 要么给原始消息的 recall range，要么明确写“earlier summary lines are not recoverable; use vcc_recall on original entries”。
4. **优先 P2 goal/constraint 账本。** 长任务需要的是“哪些约束仍然有效”，不是“这是第几次压缩”。如果 P2 继续暂停，至少保留一个跨压缩去重、可截断的 goal ledger。
5. **旧简报本身可读需要单独设计。** 例如给 compaction 摘要增加独立命名空间的 recall 模式，不占 `#N`。这与当前计划的非目标冲突，应作为独立决策，不和当前版本捆绑。

## 5. 问题三：中文用户消息和助手消息是否处于空白

### 5.1 结论

不是“完全空白”，而是“简报可见，结构化提取大面积空白”。

| 路径 | 中文结果 | 原因 |
|---|---|---|
| 简报 transcript | 正常 | 逐字渲染；1680 字中文按 `Intl.Segmenter` 截到 447 字，带 truncated 标记 |
| Session Goal | 只首条消息；后续改目标不识别；258 字单段首消息 → `[]` | 首条消息每行 >200 字被整体拒绝；后续只认英文 `SCOPE_CHANGE_RE` / `TASK_RE`（`src/extract/goals.ts:5`） |
| User Preferences | `[]` | 全英文模式（`src/extract/preferences.ts:5`） |
| Outstanding Context | `[]` | 英文 blocker 词 + 行首必须是大写拉丁字母/反引号（`src/core/build-sections.ts:21`） |
| Commits / Files / Tracked Commands | 正常 | 解析命令和路径，不依赖自然语言 |
| codemode `// goal:` | 正常 | 固定英文标记，正文自由；已有中文测试（`src/codemode/summary.ts:76`） |
| 助手消息 | 只进 brief/search | 没有结构化提取；中文 blocker 也进不了 Outstanding Context |
| recall 搜索 | 字面匹配 | 按空白切词；中文整句是一个 term，能做子串/BM25，但没有分词、同义扩展 |
| 截断 | 中文标点不识别 | `clipSentence` 只认 `.!?` + 空白，`。！？` 会退化为硬切且无省略号（`src/core/content.ts:22`） |

### 5.2 实测探针

- 三行中文首消息（每行 ≤200 字）→ 三行都进入 Session Goal。
- 258 字单段中文首消息 → Session Goal、Preferences、Outstanding Context 全部为空。
- 首条目标之后追加“改成按 Unicode 码点截断，之前的方案不要了” → 不生成 `[Scope change]`，旧目标继续显示。
- “不要使用外部依赖，保持和现有代码风格一致” → User Preferences 为空。
- 助手消息“这次修复没有成功……” → Outstanding Context 为空。
- 1680 字中文用户消息 → 简报 447 字，带截断标记；说明 brief 路径本身可用。

### 5.3 建议

1. **先补最影响正确性的三类，保持小而明确：**
   - 后续改目标：`改成 / 换成 / 改为 / 不用 / 别再 / 重新 / 不是…而是` 等。
   - 偏好：`不要 / 别 / 务必 / 总是 / 保持 / 统一` 等。
   - blocker：`失败 / 报错 / 异常 / 阻塞 / 卡住 / 未解决 / 无法 / 不能` 等。
2. **首条长消息按 `。！？；` 切句，而不是整体丢弃。** 每句仍受 200 字上限，取前若干条。
3. **`clipSentence` 识别 CJK 标点并补省略号；`clip` 在硬切时至少给出截断指示。**
4. **每类加中文夹具：** 至少覆盖“258 字单段”“改成…”“不要使用…”“这次修复没有成功”四种；同时加一条中文 recall 命中测试，不要默认它可用。
5. **注意契约。** 这些 extractor 是所有会话共用的。改它们会改变“无 codemode 记录的会话与上游一致”的承诺（计划 §3.4）。要么把中文支持定为 fork 级的显式改进并更新契约/黄金测试，要么把语言参数传进去、只在需要时启用；不要悄悄改掉上游行为。
6. **对 codemode 任务，更稳的中文目标通路仍然是 `// goal:` 账本 + P2 状态；正则只做兜底。**

## 6. 优先级与待决事项

### 6.1 建议优先级

1. **意图账本 + codemode goal 加分 + H 额度 1500–2000**：直接解决“最早意图被省略”，成本最低。
2. **中文 blocker / 偏好 / 改目标 + 长首消息 + CJK 截断**：补上长任务最危险的中文空白；先决定契约归属。
3. **预算矩阵实验**：在 200K–350K 真实会话上跑 2K/5K/10K × maxBlocks 80/200/400，按会话形状报告意图保留、总 token、旧简报保留和行为结果。
4. **覆盖声明 + 修 merge 标记**；旧简报的独立 recall 模式和 P2 状态另做设计决定。

### 6.2 需要明确决定的问题

- 中文支持是 fork 级改进，还是只在 codemode 会话启用？
- 5K 是否作为大窗口默认上限？10K 是否只做配置项？
- 旧简报是否需要可读？如果需要，是否接受新增独立 recall 命名空间？
- “意图保留”用什么指标验收：唯一 goal 数、按会话形状的保留率、还是压缩后的正确下一步/重复工作？
- 167K 样本含 context edit，定稿前是否在 Pi projection 路径上复测？

## 7. 复现方法

### 7.1 现有审计脚本

```sh
bun run scripts/codemode-brief-audit.ts \
  --sessions <session.jsonl> \
  --quota 0,1000,1500,2000,4000 \
  --out research/codemode-brief-audit.json
```

注意：脚本的 `segments` / `quota` 是**整条分支的未排名简报**口径，不能直接当作存储摘要的丢弃率。要测量实际摘要窗口，需要以最后一次 compaction 的 `firstKeptEntryId` 为边界重建窗口（见 §2.2）。

### 7.2 本次额外测量的做法

1. 从 session JSONL 沿 `parentId` 还原当前分支。
2. 找到最后一次 `type:"compaction"` 条目及其 `firstKeptEntryId`。
3. 取该边界之前的消息作为摘要窗口；用 `normalize` 转成块。
4. 用 `buildGlobalIndexById` 生成会话全局 `#N`。
5. 用 `selectRankedBriefBlocks` 复现 ranked 选块；用 `buildBriefSections` 分别以 quota 0 / 1000 / 1500 复现段渲染。
6. 只统计 codemode 行数、是否出现省略标记和摘要字符数。

含 `context_edit` 的会话不能直接这样重建：Pi 的 projection 会改写可见消息，离线脚本没有复现该路径，因此 167K 样本的绝对条数是近似值，趋势结论不受影响。

### 7.3 数据边界

- 不引用消息正文、文件路径、会话文件名。
- 审计输出只写 `research/`，该目录被 `.gitignore` 忽略。
- 真实会话数据不进入提交、PR 或本文档。

## 8. 未验证与风险

- **167K 样本的 projection 差异**：含 3 个当前分支的 `context_edit`，窗口按原始分支重建，绝对条数可能和实际摘要输入有偏差。
- **350K 真实任务**：本次没有 350K 的 codemode 会话；大窗口结论来自 167K 样本和合成压力测试。
- **行为与总成本（G3）**：没有测压缩后的正确下一步、重复调查/写入、目标偏离和总 token。
- **多次压缩的合并压力**：更大 brief 会更快触顶 120 行合并预算，旧简报保留可能进一步下降；需要和 5K/10K 一起测。
- **中文搜索**：只做了代码核对，没有做真实查询命中率测量；计划 §3.3 已将其列为未验证假设。
- **token 估算**：chars/token 被限制在 2–6，中文/代码混合会话的真实比例可能超出；预算的实际 token 成本需要真实 usage 校准。
- **旧简报可读性**：当前没有 recall 入口；任何“旧简报在哪里”的提示都必须先有检索路径，否则比不提示更危险。

## 9. 一句话总结

**60K 的痛点是“最早的 1 条被尾部优先的额度挤掉”，167K 的痛点是“170 条在 ranked 选块阶段静默消失”。前者把 H 调到 1500–2000 就够，后者需要 5K/10K + 更高的 `maxBlocks` + 意图账本；两者都不该用“第 N 次压缩”的裸提示来替代真正的覆盖与召回设计。中文方面，brief 能用，但 goal 变更、偏好和 blocker 目前基本没有进入结构化摘要。**
