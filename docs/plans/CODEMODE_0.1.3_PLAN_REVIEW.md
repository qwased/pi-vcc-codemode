# CODEMODE 0.1.3 计划审阅意见

- 审阅对象：`docs/plans/CODEMODE_0.1.3_PLAN.md`（第五稿）
- 审阅日期：2026-10-27
- 审阅结论：**需较大修订后再开工**
- 审阅范围：实施可行性、数据管道、兼容契约、验收口径、测试覆盖与工期

## 1. 总体评价

计划对问题背景、实测依据、版本边界和对外不保证事项交代得较完整，尤其有以下优点：

1. 明确区分“执行事实”和“模型声明”，并坚持事实优先、声明降权及 `(declared)` 标记；
2. 大部分改动都给出了量化发布门，而不是只描述预期效果；
3. 明确排除了状态机、自由文本 effects、无依据的完成声明和预算默认值上调，范围意识较好；
4. P3、P8本身规模较小、边界清楚，可以保留。

但第五稿仍把若干需要先改数据模型和跨模块接口的工作写成了局部算法调整。当前代码不能直接提供P1、P2、P5、P7、P10所需的全部信息，P4/P9又使用了与现状不一致的截断单位。若按现稿逐项施工，实施中必然出现新增设计决策，4.8天的估时也会失去约束力。

建议把本稿状态从“实施计划”改为“待技术设计闭环”，先解决下列阻断项。若维持全部必做范围，较可信的保守估计是 **8–12人日**，且不含真实会话复跑和发布收尾。

## 2. 阻断项

### 2.1 P1缺少“逐脚本执行效果”的关联数据，用户块硬保留也与硬预算冲突

当前标准化过程把 `toolResult` 转为只有工具名、文本和 `sourceIndex` 的块，没有保留 `nestedCalls`、`toolCallId`或结构化执行结果（`src/core/normalize.ts:28-34`，`src/types.ts:11-16`）。压缩钩子虽然读取了nested文件操作，但随即把它们聚合成会话窗口级的几个 `Set`，只把合并后的读/写文件列表传给摘要和排序（`src/hooks/before-compact.ts:733-743`、`src/hooks/before-compact.ts:764-777`）。排序函数因此只能看到块和全局文件集合（`src/core/rank.ts:102-147`），无法可靠回答“哪一个codemode脚本产生了哪一种效果”，也无法计算同一脚本的声明—执行冲突。

因此，P1不能只修改计划列出的 `rank.ts`、`before-compact.ts`、`file-ops.ts`。开工前至少要定义一个按 `toolCallId` 或明确消息索引关联的结构，例如 `EffectFact`，并写清：

- 完整nested记录如何关联到对应脚本；
- nested参数被丢弃、记录不完整、只有调用名时分别属于“事实”“未知”还是“声明兜底”；
- bash命令形状是在结构化nested调用上判断，还是在渲染文本上判断；
- 该结构如何进入normalize、rank、brief details和审计脚本。

“最近16个user块硬保留”也需要重新定义。现有选择器把recent块计入字符预算，装不下时会跳过；对应回归测试明确要求预算是真正上限，即使标为recent也可能丢弃（`src/core/rank.ts:245-279`，`tests/rank.test.ts:190-213`）。所以“user 100%”“固定预算”“字符增量不超过2%”不能同时作为无条件不变量。计划必须选择一种口径：

1. user 100%只是指定审计语料上的统计门；或
2. user块可以突破预算，但要给出最大突破上限；或
3. 预算仍是硬上限，把“硬保留”改为“最高优先级，装不下时按新到旧取舍”。

推荐第3种，并把发布门改成“审计语料上100%，算法层面不承诺任意输入100%”。

### 2.2 P2的压缩血缘范围没有可靠、可持久化的数据来源

当前 `#N` 空间只计算 `type:"message"` 条目（`src/core/global-indices.ts:16-18`），range召回也只在这一索引空间筛选消息（`src/core/recall-run.ts:228-272`）。现有压缩details仅记录版本、区段、源消息数和少量状态，不含本次被压缩消息的起止 `#N`（`src/details.ts:3-10`，`src/hooks/before-compact.ts:822-832`）。

这意味着计划所写“从 `type:"compaction"` 派生 `range:[from,to]`”对旧压缩并不成立；仅凭 `sourceMessageCount` 和 `firstKeptEntryId` 也不能在分支、重试、context edit或旧版details存在时无歧义还原范围。

建议改为：

- 从0.1.3起把已验证的 `sourceRange` 持久化到版本化details；
- 写清两端验证规则、分支作用域和旧details降级行为；
- 旧压缩或端点无法验证时只显示计数和检索建议，不伪造range；
- 明确血缘行存放位置和跨三次压缩的去重键，避免每轮增长。

完成该设计前，P2的“连续3次压缩只出现一次”和“范围可召回”无法形成可实现的确定性验收。

### 2.3 P5不是格式化小改，而是区段数据模型迁移

`NormalizedBlock`已经有 `sourceIndex`，但所有摘要区段仍是 `string[]`（`src/types.ts:11-16`，`src/sections.ts:1-11`）；Session Goal合并又直接对完整字符串做 `Set` 去重并裁尾（`src/core/summarize.ts:79-87`）。文件活动同样先汇总进 `Set`，重复项不会自然更新时序，也会丢失出处（`src/extract/files.ts:58-86`）。

所以“给目标和文件条目加 `sourceIndex`、渲染 `(#N)`、去掉ref后去重、最近优先”会同时影响提取类型、区段类型、格式化、跨压缩合并、溢出标记和测试。计划当前只点名局部函数，低估了共享类型迁移。

建议先定义统一的带来源条目，例如 `{ text, sourceIndex?, firstSeen?, lastSeen? }`，再分别规定：

- Session Goal按去ref文本去重，第1条原始目标永久保留，其余按最近性裁尾；
- Files按规范化路径去重，重复触达更新 `lastSeen`，但不把ref当作键的一部分；
- `(+N more; #A–#B)`只有在被省略集合的两个端点都能验证时才显示范围；
- 旧摘要中没有ref的字符串如何迁移和合并。

### 2.4 P5的Created修法不充分，P5b按现有声明语法无法生成路径事实

计划对“Created恒空”的根因判断只对了一半。当前 `write` 同时被归入modified和created（`src/extract/files.ts:19-26`、`src/extract/files.ts:68-76`），随后新鲜区段和跨压缩合并各删除一次created中的modified路径（`src/core/build-sections.ts:48-60`，`src/core/summarize.ts:146-153`），所以Created确实会被清空。

但“优先用hook的 `createdFiles`”目前没有来源：hook传入的只有read和modified（`src/hooks/before-compact.ts:764-771`），nested文件操作也只有read/written/edited三类（`src/codemode/file-ops.ts:4-8`）。如果只删掉 `created.delete(modified)`，普通write会同时显示为Created和Modified，并不比现在更准确。

建议本版先承认“是否新建”是未知状态，除非宿主或工具调用提供可验证的创建事实；不要用工具名 `write` 自动推断文件此前不存在。可以把修订目标改为“消除Created恒空的伪精确语义”，而不是强行恢复Created分类。

P5b也有同类问题。`// effects: delete|rename` 只有效果类别，没有源路径和目标路径，无法支持计划中的 `Deleted: a.ts` 或 `Renamed: a.ts → b.ts`。若又拒绝解析通配符、变量和重定向，就不能从任意bash文本稳定补齐操作数。建议将P5b整体延期；若必须实施，则需要扩展为结构化声明语法并单独设计转义、路径规范化和冲突规则，不能仍按0.2天估算。

### 2.5 P4/P9把“有效词预算”误写成了“字符预算”

`TRUNCATE_USER=256` 当前传给 `Intl.Segmenter` 驱动的有效词计数函数，不是字符裁剪（`src/core/brief.ts:27-74`、`src/core/brief.ts:302-310`）；现有测试也用300个英文词验证截断（`tests/brief.test.ts:258-265`）。因此“头160字符+尾96字符”和“258字消息”的验收并不是对现有常量的等价替换，而是一次截断语义变更。

P4还存在边界缺口：超过200字符的单行会在目标提取阶段直接被过滤（`src/extract/goals.ts:32-40`、`src/extract/goals.ts:51-57`）；现有 `clip` 只避免拆开UTF-16代理对且不加省略号，`clipSentence` 只识别英文 `.?!` 后接空白（`src/core/content.ts:4-14`、`src/core/content.ts:22-33`）。

计划应先统一以下口径，再写数值：

- brief用户块按有效词、Unicode码点还是字素簇截断；
- Session Goal按UTF-16长度还是可见字符长度判限；
- 无标点长段落如何兜底；
- emoji、组合字符、CJK标点是否允许被拆分；
- 省略标记是否计入预算。

推荐把P4和P9合并成一个“文本边界与截断语义”实施项，先固定共享工具和测试矩阵，再分别接入Goals和Brief。

### 2.6 P10/P7缺少结构化解析结果、拒绝原因和统计传递路径

现有声明解析器只返回 `string | null`（`src/codemode/intent.ts:9-15`），生产调用点目前只用于codemode摘要渲染（`src/codemode/summary.ts:82-88`）。它既不能区分“未声明、未知token、超长、位置非法”，也不能携带effects或blocked，更不能记录mismatch。

审计脚本当前主要直接构造brief和额度统计（`scripts/codemode-brief-audit.ts:150-191`、`scripts/codemode-brief-audit.ts:204-218`），没有走完整rank决策。因此，P7要求的声明覆盖率、冲突率和分组存续率不能靠给现有结果对象加字段完成。

建议先把P10定义为基础数据模型：

```ts
type DeclaredMetadata = {
  goal?: string;
  effects: EffectToken[];
  blocked?: string;
  rejected: DeclarationRejection[];
};
```

解析器负责封闭词表、长度和位置校验；执行事实关联层负责冲突判断；build-sections负责blocked呈现；rank只消费已经判定好的效果等级；audit消费同一批结构化判定结果。这样才能保证线上行为和审计口径一致。

### 2.7 P6不是三个常量改名，需要补完整配置生命周期

现有设置需要同时维护接口、默认值、读取时校验、配置脚手架和测试（`src/core/settings.ts:10-68`、`src/core/settings.ts:82-125`）。新增三个数值旋钮还必须传过hook、compile、buildSections和brief，并在README解释单位、范围及非法值处理。计划中的0.2天不足以覆盖这些工作。

建议与P3合并：先把默认1500作为同一个配置项落地，避免先改硬编码再立即配置化；同时明确数值应为有限非负整数，以及ceiling不得低于floor等交叉约束。

## 4. 契约与发布门的矛盾

计划一方面在P1验收中要求“<73块小窗口逐字不变”、在P2中要求“无codemode会话逐字不变”，另一方面又明确让P1、P4、P5、P9影响所有会话，并在契约章节把兼容承诺降级为“格式与提取规则一致，bug修复除外”。仓库README当前仍写着“Non-codemode sessions are unchanged”（`README.md:261-269`）。

这三种表述不能同时成立。建议用一张精确例外表替代笼统承诺：

| 会话形态 | 允许变化 | 必须不变 |
|---|---|---|
| 无codemode、小窗口、未触发P4/P5/P9边界 | 无 | 摘要逐字一致 |
| 无codemode、命中长段落/Created/用户截断边界 | 对应bug修复输出 | 其他区段及排序不变 |
| 有codemode、无声明 | P1/P2/P3规定的fork行为 | 声明相关输出和计数为空 |
| 有codemode、有声明且事实完整 | 声明可显示，但事实优先 | 冲突时不得改变事实分类 |
| 有codemode、nested不完整 | 仅允许声明兜底并标记 `(declared)` | 不得把未知渲染成执行事实 |

发布门中的“逐字不变”应只用于第一行，其余使用定向golden或结构化断言。

## 5. 建议的实施顺序

原计划按P编号推进会反复修改同一条数据管道。建议改为四个阶段，每阶段通过测试门后再进入下一阶段。

### 阶段A：基础数据模型与配置

1. 结构化声明解析：goal/effects/blocked、拒绝原因、长度和封闭词表；
2. 逐脚本执行事实及声明冲突模型；
3. 带来源的SectionItem和版本化lineage details；
4. P3/P6配置schema、默认值、校验和全链路传递。

**阶段门**：类型检查通过；声明和EffectFact单元测试完整；旧details、旧配置可读取；默认配置输出与基线一致，P3明确例外除外。

### 阶段B：提取与呈现

1. P4/P9统一文本边界和截断工具；
2. P5目标/文件出处、跨压缩去重和最近性；
3. blocked进入Outstanding Context；
4. Created仅在存在可验证创建事实时显示；P5b延期。

**阶段门**：长中英文、无标点、CJK标点、emoji/组合字符、原始目标永久保留、旧摘要无ref合并均有golden测试。

### 阶段C：排序与召回

1. P1消费已经关联好的执行事实和声明，不在rank中重新解析；
2. 明确user优先级和预算失败行为；
3. P2生成覆盖说明、血缘行和不可召回说明；
4. P3额度由配置注入。

**阶段门**：预算装不下16个user块、nested完整/不完整/参数丢失、声明一致/冲突、三次压缩、分支/context edit和旧details全部通过。

### 阶段D：度量、文档与发布

1. P7审计复用生产分类函数，生成计划列出的曲线；
2. P8更新README、CHANGELOG、AGENTS和版本；
3. Pi 1.0.0与锁定1.4.0双跑；
4. 用本地聚合数据复现阈值，但不得输出会话正文。

## 7. 工期复核

现稿4.8天没有计入以下工作：共享类型迁移、EffectFact关联、lineage details版本化、配置校验与全链路传递、审计复用生产逻辑、旧摘要兼容以及上述边界测试。建议在完成阶段A技术设计后重新估时。

在不降低范围的前提下，可暂按以下量级规划：

- 阶段A：2.5–3.5天；
- 阶段B：2–3天；
- 阶段C：2–3天；
- 阶段D：1.5–2.5天；
- 合计：约8–12人日。

若必须维持约5天，应至少延期P5b、P7完整曲线和P2历史range，只交付：结构化声明最小版、P3/P6、P4/P9边界修复、P1的可验证事实分档，以及相应文档。

## 8. 最终意见

本计划的产品方向成立，实测数据也足以支持继续推进；问题主要不在“要不要做”，而在“现有数据从哪里来、如何跨压缩保存、预算冲突时遵循哪个不变量”。建议在第六稿中完成以下四项后再批准实施：

1. 增加EffectFact、DeclaredMetadata、SectionItem和lineage details的准代码与目标文件；
2. 明确user保留、字符预算和2%增量三者的优先级；
