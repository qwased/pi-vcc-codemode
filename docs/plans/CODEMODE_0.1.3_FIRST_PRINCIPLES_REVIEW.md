# CODEMODE 0.1.3 第一性原理评估与重建建议

- 日期：2026-10-27
- 审阅对象：`CODEMODE_0.1.3_PLAN.md` 第五稿、`CODEMODE_0.1.3_PLAN_REVIEW.md`
- 文档性质：独立评估与重建建议，不取代原计划，不修改上述文档
- 核心结论：**重建计划，收缩 0.1.3；暂不重写整个压缩系统。**

## 1. 总体判断

原计划的产品方向成立：长程任务需要知道做过什么、当前要做什么，以及缺失信息到哪里找。现有审阅对数据关联、持久化、配置生命周期、截断单位和工期的质疑也基本必要；本文核对到的关键源码事实与其一致。

但仅在第五稿上补 `EffectFact`、`DeclaredMetadata`、`SectionItem` 和 lineage details，再把工期改成 8–12 人日，仍然不够。这样会把“功能过多、事实层级混杂、指标与目标不一致”的计划，变成“基础设施更多、实施周期更长”的计划。

需要先改变计划的组织方式：

1. 从“还能加入哪些摘要特征”改为“后续任务需要什么信息，这些信息如何被可靠地产生、保存、淘汰和召回”。
2. 从“某类条目保留率越高越好”改为“在硬预算内，尽量保留后续需要且缺失代价高的信息，同时不制造假事实”。
3. 从“声明与事实二分”改为“调用、结果、派生状态、模型声明、未知”分层。
4. 从“把所有基础模型一次建好”改为“每个可发布竖切都闭环：数据来源 → 跨压缩行为 → 渲染 → 召回 → 验收”。

因此，不建议按原计划全量实施，也不建议按现评审的四阶段全量实施。建议把 0.1.3 定义为一个**可信性与可验证性版本**，只纳入能够证明信息来源和失败降级的改动；当前任务状态、完整声明族和精确血缘另做设计。

## 2. 从第一性原理重新界定问题

### 2.1 摘要、原始历史和召回不是同一种存储

应先把四个角色分清：

| 角色 | 应承担的责任 | 不应承担的责任 |
|---|---|---|
| 原始会话 | 保存仍可读取的历史记录，是召回的数据来源 | 不代表外部文件系统此刻的状态，也不保证写入时已丢弃的数据能恢复 |
| 压缩摘要 | 在固定预算内提供继续任务所需的工作集和导航 | 不可能保存全部历史，也不应伪装成完整事实数据库 |
| 派生状态 | 保存需要跨压缩合并的少量状态及其来源、新鲜度 | 不能把历史调用直接当成当前事实 |
| `vcc_recall` | 按需修复摘要的信息损失 | 不能恢复宿主未保存或生成时已截断的内容 |

在这个结构中，摘要条目是否值得保留，取决于三个因素：

> **后续需要它的概率 × 缺失时的恢复或出错成本 − 它挤占其他信息及误导模型的成本。**

“写类脚本保留率应当不低于只读脚本”不是从这个目标推出的不变量。某些只读结果决定了根因，某些写调用只是失败尝试或重复操作；两类条目的最优保留率没有理由必须相等。

同样，算法可以验证“信息是否保留、是否可追溯、是否超出预算”，却不能仅凭这些指标宣称“模型仍知道”。模型是否利用这些信息继续任务，需要单独的行为评估；没有行为评估时，发布说明应只声称信息保留和导航能力得到改善。

### 2.2 “事实”至少需要四层，外加未知

原计划只有“执行事实”和“模型声明”两类，不足以支撑它想要的语义。

| 层级 | 示例 | 可以得出的结论 | 不能得出的结论 |
|---|---|---|---|
| 观测到的调用 | nested `write`、`bash` 中出现 `rm` | 某次调用被记录，命令具有潜在变更形状 | 操作成功、文件已创建或已删除 |
| 观测到的结果 | nested `status`、工具错误、退出码 | 某个被记录的结果成功、失败或不完整 | 后续没有外部改动，当前文件仍处于该状态 |
| 派生的最后已知状态 | 最后已知阻塞、最后已知目标、文件活动汇总 | 在某个来源和时点观察到或推断出的状态 | 永远有效、无需淘汰或重新确认 |
| 模型声明 | `// goal:`、`// effects:`、`// blocked:` | 模型曾作出该声明 | 声明正确、完整、未过期 |
| 未知 | nested 参数被丢弃、旧摘要无出处 | 当前信息不足 | 用确定措辞补齐缺失语义 |

`verify` 也只能说明调用目的，不能压制或改写失败结果。一次验证失败可能是预期的红灯，也可能是真正的阻塞；无论哪种情况，“声明为 verify”都不能推出“失败可以忽略”。否则就会出现声明实际改变事实呈现，与原计划自己的最高纪律相冲突。

### 2.3 必须先固定的不变量

1. **预算是实际渲染结果的硬上限。** 评分可以使用效用权重，预算扣减必须使用最终真实成本；不能用打折后的成本证明没有超预算。
2. **不确定就显示不确定。** 工具名、命令形状和声明都不能升级为成功结果或当前状态。
3. **出处必须能解析。** `#N` 只负责定位消息；范围如果只是边界，就不能称为精确的压缩输入集合。
4. **重复压缩必须有界。** 注释、血缘、条目数和派生状态都不能随压缩次数无条件增长。
5. **易变状态必须有生命周期。** 当前目标、阻塞、完成和删除语义都需要来源、新鲜度、保留及失效规则。
6. **兼容例外必须逐条列举。** “bug 修复除外”不能成为吞掉所有非 codemode 行为变化的兜底条款。

## 3. 原计划和现评审仍未解决的关键问题

### 3.1 指标优化对象与版本目标不一致

原计划中的 `goal` 同时容易被理解为脚本 `// goal:` 存续率和 `[Session Goal]` 质量，两者不是一回事。写类保留率、用户块保留率、字符数和声明覆盖率也都是摘要形态指标，不是“减少重复调查、目标偏离、无效 recall”的直接测量。

主要风险有三个：

- 在同一本机语料上选择 `+12`、`+14` 等参数，再用同一语料要求提升，容易把调参结果当成独立验证。
- 汇总条数会被长会话和高频脚本主导；应同时看每个会话的配对变化和退化分布。
- 只报告某类保留率上升，无法说明它挤掉了什么。保留率相等也不代表信息价值相等。

这些指标可以保留为诊断量，但不应继续充当核心目标或泛化发布门。

### 3.2 P1 把“潜在变更调用”误称为“执行效果”

`write/edit`、`rm/mv`、`git commit|push` 等名称或命令形状，即使来自真实 nested 记录，也首先证明“调用了什么”。它们不自动证明副作用成功。工具状态可以进一步证明某个结果，但仍不能证明当前外部状态。

因此 P1 可以做“按潜在任务价值调整活动条目的排序”，不能直接做“效果事实分档”。渲染和度量也应分别使用 `invoked`、`observed_result`、`unknown`，避免实现和文档再次混用。

### 3.3 逐脚本关联不能用 `#N` 代替调用身份

当前标准化会丢失 `toolCallId` 和 `nestedCalls`，而同一 assistant 消息中的多个 tool call 会共享同一个 `sourceIndex`（`src/core/normalize.ts:28-34`、`src/core/normalize.ts:43-55`）。因此：

- `toolCallId` 应用于配对调用与结果；
- `#N/sourceIndex` 应用于显示和召回；
- 不能仅以消息序号充当逐脚本执行记录的唯一键。

现有 recall 已按 `toolCallId` 配对展开调用与结果（`src/core/recall-run.ts:170-217`），新设计应复用这一关联语义，而不是另造一套窗口位置规则。

### 3.4 `blocked` 和“永久原始目标”已经引入状态问题

原计划把状态机推迟到 0.2.0，但 `// blocked:`、原始目标永久保留和 `[Outstanding Context]` 本身就已经是状态语义。

当前跨压缩合并对 `[Outstanding Context]` 只取 fresh（`src/core/summarize.ts:59-62`）。这意味着新声明的 blocked 若不再次出现在后续窗口，就会在下一次合并时消失；如果简单改成永久继承，又会长期保留已经解决的阻塞。`(declared)` 只说明来源，不能解决过期问题。

“第 1 条永久保留 + 最后 7 条”可以保存目标历史，却不能保证当前要做什么。原始需求、后续 scope change 和当前未完成工作必须分开命名，不能由一个 `[Session Goal]` 队列兼任。

### 3.5 成本折扣与硬预算是两套账，不能混用

原计划写“变更类块成本 ×0.8 或封顶 120 字符”，既存在未选择的二选一，也没有区分两种用途：

- 在价值排序中给某类信息更高的单位成本效用，可以作为候选启发式；
- 在 `usedChars` 中少记真实输出，则会破坏硬预算。

当前选择器明确把 recent 块也按真实渲染成本计入预算，装不下会跳过（`src/core/rank.ts:245-280`；`tests/rank.test.ts:190-213`）。新计划应保留这一不变量，并把“用户 100%”限定为指定语料上的观察结果，而不是任意输入的算法承诺。

### 3.6 一个全局 `#N` 范围不等于精确压缩血缘

旧 details 没有可靠范围，现评审已经指出。还需补充分支问题：全局 `#N` 按会话文件中的所有 message 条目计数，包括其他分支（`src/core/global-indices.ts:16-18`、`src/core/global-indices.ts:50-57`）。因此首末索引之间的范围可能只是**包围范围**，其中可以夹杂非本分支或不属于本次压缩的条目。

如果 recall 只返回 active lineage，它又不会自动呈现范围内的所有 off-path 条目。故 `range:[from,to]` 不能在未定义作用域时被宣传为“本次压缩的完整输入”。

0.1.3 不应为旧压缩反推范围。即使为新压缩持久化首末点，也必须称其为有作用域的边界；若未来需要精确重放，应设计真正的 compaction 输入身份或有界成员记录，而不是只加两个数字。

### 3.7 新声明的预期收益缺少交集证据

`effects` 兜底只服务于“执行记录不完整，同时模型写了合规声明”的交集。原计划分别给出了 nested 参数缺失比例和其他声明的合规率，但没有给出这个交集，也没有证明新声明在该交集中的正确率。

因此，目前无法判断新增 prompt 规则、解析器、冲突统计和渲染复杂度能换来多少实际覆盖。声明覆盖率、冲突率也需要同时报告不可验证比例；只能在有执行记录时发现的冲突，不代表其余声明都正确。

### 3.8 P6 的既定用途不需要立刻增加公开配置

如果 P6 只是为了离线实验，现有代码已经有内部注入口：`BriefRankingOptions`、`BriefBuildOptions`，审计脚本也已有 `--quota` 参数（`src/core/rank.ts:5-33`、`src/core/brief.ts:256-264`、`scripts/codemode-brief-audit.ts:30-40`）。优先补齐审计对完整生产管线的复用即可。

公开设置会增加校验、迁移、文档和长期兼容成本，不应仅为开发者调参而提前冻结。若未来确有用户调节需求，再作为独立配置项目完成完整生命周期。

### 3.9 现评审的“阶段 A 全量基础设施”仍然偏大

现评审正确识别了缺失的数据模型，但建议在一个阶段同时完成声明、执行事实、区段条目、血缘和配置，再进入呈现与排序，仍然会形成大范围耦合改造。

更好的顺序不是“先设计所有类型”，而是每个竖切只引入自己需要的最小结构，并回答完整生命周期。例如，文本截断修复不需要等待 EffectFact；Created 语义修正也不需要等待声明解析器。只有确实跨多个消费者共享的结构，才上升为公共模型。

## 4. 建议的 0.1.3 重建方案

### 4.1 重新表述版本目标

建议改为：

> **在不伪造执行结果和当前状态的前提下，修复关键文本与文件活动的失真，明确召回边界，并用同一生产管线验证一个 codemode 排序候选。**

这个版本不承诺一次性解决“当前任务状态”“精确历史血缘”“完整声明语义”。这些目标需要另一套生命周期设计。

### 4.2 M0：先建立可比较的基线，再改排序

这是前置工作，不再是最后的 P7 附属项。

1. 固定基线版本、语料选择规则、窗口构造、预算单位和指标定义；明确 `script-goal retention` 与 `Session Goal` 是不同指标。
2. 审计复用完整生产压缩与排序路径。当前已提交脚本主要直接构造 brief、读取已存摘要，并未执行 `selectRankedBriefBlocks`（`scripts/codemode-brief-audit.ts:204-218`、`scripts/codemode-brief-audit.ts:271-317`），不能直接复现 P1 的完整选择结果。
3. 输出每个会话的配对差值、退化数量和中位数/高分位，而不只输出 pooled 条目比例；真实会话仍只写聚合结果，不输出正文。
4. 调参语料与最终验证分离。样本不足时只做敏感性报告，不宣称统计显著或普遍收益。
5. 建立带“必须保留、可以丢弃、必须判未知”标签的合成场景，作为确定性发布门。

### 4.3 C1：合并 P4/P9，修复文本边界，但不强迫所有场景同单位

1. 明确 Goals 的条目上限、Brief 的有效词预算和 Unicode 安全边界分别是什么；统一术语和共享边界工具，不要求语义不同的场景强行使用同一数值单位。
2. 覆盖 CJK 标点、无标点长段、组合字符、emoji、省略标记计入上限，以及短文本逐字不变。
3. 首条消息保留几行由场景测试决定，不把“6 改 8”本身当成目标；必须验证后续 scope change 不会被原始需求挤出。

### 4.4 C2：先修事实与召回边界，不做伪精确血缘

1. **Created：**没有可验证创建事实时，不从 `write` 推断“此前不存在”。可以只记录历史 `Written/Modified` 活动，或明确显示未知；不要仅靠删除 `created.delete(modified)` 让同一路径同时进入两类。
2. **召回说明：**保留一条短、可行动的 `RECALL_NOTE`。图片、写入时截断、nested 参数缺失等详细限制优先放在工具文档和具体失败输出中；只有能改变模型下一步行动的限制才进入每轮摘要，避免免责声明本身持续占用预算。
3. **旧压缩：**只给可验证计数和检索建议，不生成 range。
4. **新压缩：**只有在明确消费者、分支作用域、存储上限和降级行为后，才持久化新的血缘字段；否则本版不预先保存无人使用的数据。
5. **覆盖与省略说明：**连续压缩只出现一次，所有新增 note 变体都能被旧摘要合并逻辑剥离。

### 4.5 T1：出处与最近性作为独立竖切，不和 Created 捆绑

1. 为 Goals/Files 定义带来源的最小条目结构，说明 fresh、previousSummary 和无 ref 旧摘要如何合并。
2. 去重键与显示 ref 分离；文件按规范化路径维护最近性，目标按文本与来源规则处理。
3. 原始请求若保留，应显式标为历史起点并限制为一条；近期目标和 scope change 另行保留，不宣称它们就是已验证的当前状态。
4. 溢出范围只有在端点和集合语义都可验证时才显示，否则只给数量与可解析的代表性 refs。

这个竖切可以进入 0.1.3，但不应为了赶上版本而绕过旧摘要合并测试；未完成时与 C1/C2 解耦发布。

### 4.6 E1：只验证一个无新声明的排序候选，P3 与其联合验收

1. 用 `toolCallId` 关联调用和结果，`sourceIndex` 只负责出处。
2. 区分潜在变更调用、观测结果和未知；bash 形状只作为排序启发式，不生成 Created/Deleted/Renamed 等结果事实。
3. 不引入 `effects`、`blocked`、`verify` 兜底，先测纯观测数据能带来多少收益。
4. 用户块是预算内高优先级，不承诺任意输入 100%；必须测试单个用户块过大、16 个用户块装不下以及它们挤掉关键结果的场景。
5. 评分效用和真实预算记账分开，最终渲染始终不超上限。
6. P3 的 1000→1500 与排序候选在同一集成管线中评估，因为二者共享预算并会互相挤占；不将单独测得的收益直接相加。
7. 只有合成场景无退化、配对聚合结果有净收益且字符/预算门通过时才合入。未通过就保留实验结果，不为了完成 P1 而继续加分值。

### 4.7 R1：最后更新契约和发布说明

1. 对非 codemode 会话列出逐条 golden 例外，不用“bug 修复除外”概括所有差异。
2. README 只声称已被测试支持的能力；没有行为统计时，不写“保证模型不偏离”。
3. 更新 CHANGELOG、AGENTS.md 规则和版本，完成 Pi 1.0.0 与锁定 1.4.0 双跑。
4. 工期在 M0 和竖切边界确定后重新估算。4.8 天与 8–12 天都不应沿用来约束一个已经改变范围的版本。

## 5. 原实施项的处理建议

| 原项 | 建议 | 原因 |
|---|---|---|
| P1 | **重做后作为 E1 候选** | 保留观测驱动的排序实验，去掉效果误称、声明兜底和写/读相等发布门 |
| P2 | **拆分** | note 与不可召回边界可保留；旧 range 删除，新血缘按精确语义另设计 |
| P3 | **与 E1 联合验收** | 不是孤立常量改动，会和排序及合并预算相互作用 |
| P4 + P9 | **合并为 C1，优先做** | 是清楚的文本正确性问题，但需先固定单位和 Unicode 边界 |
| P5 | **拆成 C2 与 T1** | Created 是事实修正；出处/最近性是数据迁移；原始目标永久保留不是当前任务方案 |
| P5b | **延期** | effects 类别没有路径与成功结果，无法生成可靠删除/重命名事实 |
| P6 | **本版不做公开旋钮** | 离线实验已有内部注入口；公开配置应等待真实用户需求 |
| P7 | **前移并重建为 M0** | 必须复用生产管线，且指标只能作诊断，不能替代任务场景 |
| P8 | **保留为 R1** | 行为稳定后更新契约、文档和版本 |
| P10 | **新 effects/blocked 本版延期** | 收益交集未证实，blocked 生命周期未定义，verify 不得压制失败 |
| P9b | **另做结果语义设计** | 先区分调用、结果和预期，不做未修复推断 |
| P11 | **继续延期** | next 是典型易变状态，不能只加 `(declared)` 就解决过期 |

## 6. 新的验收体系

### 6.1 硬发布门：确定性不变量

- 实际渲染预算不超限，任何优先级和效用权重都不能绕过。
- 观测调用、观测结果、派生状态和声明在数据与渲染上不互相冒充。
- 无法验证时不输出创建、删除、重命名、精确范围或当前状态。
- 所有输出的 `#N` 能解析到预期消息；off-path 有明确作用域说明。
- 连续 1、3、5 次压缩后，note、状态和历史条目的增长均有界。
- 无声明时，不新增声明相关输出；无 codemode 且未命中明确修复边界的 golden 逐字不变。
- Pi 1.0.0 与 1.4.0 的类型检查和测试均通过。

### 6.2 任务信息场景：检验“保留了什么”，而非只检验保留率

| 场景 | 必须断言的结果 |
|---|---|
| 原始需求后发生 scope change | 原始需求仍可追溯，最新方向不会被错误标成旧目标，也不会被首条永久保留挤掉 |
| 长单段中文/英文需求，末尾含验收标准 | 关键首尾按既定边界保留，省略位置明确，无 Unicode 破损 |
| 写工具被调用但返回失败 | 不得渲染成成功修改；失败证据仍在 |
| `verify` 目的声明与失败结果同时存在 | 失败不得被声明压制，预期与否标为未知或声明 |
| 同一 assistant 消息含多个 codemode 调用 | 每个调用与各自结果关联，#N 相同也不会串线 |
| nested 完整、不完整、只有名称、参数被丢弃 | 每种形态进入既定事实层级；声明无法覆盖已有结果 |
| blocked 后经历无关压缩 | 按明确规则保留、降级为历史或淘汰；不得无规则消失，也不得永久冒充当前阻塞 |
| 分支重试、context edit、旧 details | 不伪造血缘；范围与 off-path 行为符合定义 |
| 用户块总成本超过预算 | 预算仍是上限，有确定的淘汰结果，不承诺 100% |
| P3 与排序共同启用 | 直接工具 8 条规则不变，codemode 恢复与整体预算均符合预期 |

这些场景证明的是信息可用性和诚实性，不是模型行为本身。

### 6.3 聚合诊断：报告方向和退化，不设伪自然定律

保留以下指标，但改名、分组并明确口径：

- 用户块、脚本 goal、潜在变更活动、只读活动、未知记录的存续率；
- 每个会话的配对变化、退化会话数、中位数与高分位摘要成本；
- 文件段形态、出处可解析率、溢出率；
- 声明采用率、可验证冲突率、不可验证比例；
- 省略条目的召回覆盖率与不可恢复原因。

“写类 ≥ 只读”“任意输入 user 100%”不再作为通用门。若某个固定审计集仍采用这些阈值，必须同时给出语料、基线和被挤掉条目的退化报告。

少量配对行为跑分可以作为人工冒烟和案例记录，但不因做了六次就获得统计结论，也不因没有统计力就完全失去价值。它不能替代上述确定性场景。

## 7. 何时才需要重建底层压缩架构

如果后续版本仍把“反复压缩后知道当前要做什么”作为核心目标，就需要正面处理状态转移，而不是继续扩张字符串补丁：

```text
S(n+1) = reduce(S(n), newlyCompactedObservations)
summary(n) = render(S(n), rankedRecentEvents, budget)
```

其中：

- `S(n)` 是有界、版本化、可降级的派生状态，可存于 compaction details；
- 原始会话仍是历史证据来源，派生状态不是外部世界的绝对真相；
- 不可变事件、最后已知状态、模型声明和导航元数据分别有自己的合并与失效规则；
- 摘要只是状态和近期事件的视图，不再同时充当唯一数据库、唯一迁移格式和唯一去重键；
- 旧摘要无法提供的信息必须标为 legacy/unknown，不能通过猜测补齐。

这属于另一次架构设计，不应偷偷塞进 0.1.3。也不意味着现在就要建立一套覆盖所有区段的大而全类型系统；应先由当前目标或阻塞的一个完整竖切证明该状态模型确有必要。

## 8. 最终建议

1. **不批准第五稿直接施工。** 它的问题不仅是漏了几个类型，而是目标、事实语义、状态生命周期和验收指标尚未对齐。
2. **也不建议按现评审维持全范围并扩到 8–12 人日。** 这会放大一个尚未证明收益的版本。
3. **按 M0 → C1/C2 → T1/E1 → R1 重建实施计划。** C1/C2 可独立交付；T1/E1 未过各自门就减量，而不是追加未经论证的补救规则。
4. **新声明族、精确血缘和当前任务状态另立设计。** 在这些语义闭环前，0.1.3 只做可验证的改进。
5. **发布承诺与证据强度一致。** 本版最可信的目标是“更少失真、更可追溯、预算与降级可验证”，而不是“已经保证长程任务不偏离”。
